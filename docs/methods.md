# 문제 접근과 검증 설계

## 1. 확률 예측으로 문제를 정의하기

목표는 투구마다 제구 성공 확률을 출력하는 것이다. 성공·실패를 0.5 임계값으로 나누는 분류 정확도보다,
예측한 확률이 실제 결과와 얼마나 가까운지가 중요했다.

공식 [평가 방식](https://dacon.io/competitions/official/236743/overview/evaluation)은 다음과 같다.

```text
Brier = mean((예측 확률 - 실제 0/1 결과)^2)
r = 해당 평가 데이터의 평균 성공률
Score = max(0, 100000 × (1 - Brier / (r × (1-r))))
```

이때 `r`은 평가자가 지표를 계산할 때 사용하는 값이다. 추론 코드에서 test 전체의 평균을 추정해 행별 예측을 보정하는 데 사용하는 값이 아니다.
연도별 내부 점수도 해당 검증 연도의 기준값으로 계산하므로, 서로 다른 평가셋의 환산 점수를 그대로 비교하지 않았다.

## 2. 피처를 정보의 종류와 시점으로 나누기

| 피처 묶음 | 예시 | 실험에서 확인한 질문 |
|---|---|---|
| 경기 상황 | 볼·스트라이크·아웃, 이닝, 주자, 점수 차 | 투구 직전 상황이 성공 확률을 얼마나 설명하는가? |
| 선수·상대 특성 | 투수·타자 ID, 손 유형, 팀 | 선수 고유 성향과 상대 조합이 도움이 되는가? |
| 누적 이력 | `asof_*` 성공·실패 유형 비율과 표본 수 | 과거 평균을 어느 정도 신뢰할 수 있는가? |
| 최근 상태 | 직전 1·3·5경기 기록 | 최근 상태 변화가 장기 수준을 넘어서는 정보를 주는가? |
| 과거 물리 이력 | 구속, 릴리스, 무브먼트, 구종 구성 | 신뢰할 수 있는 연결·시점 조건에서 추가 신호가 있는가? |
| 상호작용 | 카운트×상태, 좌·우타 상대 효과, 경기 유형 | 전체 평균 모델이 놓치는 구간별 차이가 있는가? |

현재 투구가 끝난 뒤에 알 수 있는 위치·결과·실제 구종·물리 측정값은 입력에서 배제했다.
과거 이력의 결측에는 관측 수와 이력 유무를 함께 두어, 기록이 없는 상태를 낮은 성공률과 구분했다.

초기 EDA에서는 main과 TrackMan의 ID가 직접 대응하지 않는다는 점을 확인했다.
후속 실험의 이력 대응이나 target-free 물리 표현은 이 문제를 해결하기 위한 별도 가설이며,
공식 연결표가 존재했다거나 같은 숫자 ID를 그대로 조인했다는 뜻이 아니다.

## 3. 트리 모델과 딥러닝에 다른 역할 부여하기

트리 계열에서는 범주형·수치형 혼합 입력과 도메인 파생값을 다뤘다. CatBoost 기준선은
피처 수와 순서, seed, 학습 설정을 고정해 이후 변화의 효과를 비교했다.
LightGBM·XGBoost는 단일 성능과 함께 기존 모델과 다른 오차가 있는지 살폈다.

딥러닝에서는 FT-Transformer의 피처 표현, RealMLP의 보정·학습 설정, SAINT의 attention 범위 등을 검토했다.
앙상블 계열에서는 DCN·DeepFM·TabM·RoleState·latent-pitch·RealMLP와 상황별 expert를 구성 요소로 활용했다.
단일 모델 실험과 앙상블 안의 구성 모델은 학습 조건이 다를 수 있어 동일 모델명만으로 결과를 대응시키지 않는다.

## 4. 시간 순서 검증과 후보 선택

| Fold | 학습 | 검증 |
|---|---|---|
| 1 | 2019–2021 | 2022 |
| 2 | 2019–2022 | 2023 |
| 3 | 2019–2023 | 2024 |

피처의 통계·범주 사전도 fold의 학습 부분에서 적합한다. 전체 데이터를 먼저 변환한 뒤 분할하면
모델 학습 전에 검증 정보가 들어갈 수 있기 때문이다.

여러 실험에서 2022·2023을 개발 구간으로 사용하고 2024로 확인했다. 다만 후속 탐색에서 2024를 반복해서
관찰한 경우에는 사후 확인으로 기록했다. 모든 실험이 처음부터 동일한 미관측 holdout을 유지했다고 주장하지 않는다.
또한 후반 JJO 일부 실험은 고정 보정 크기를 선택하는 데 Public 피드백을 사용했다고 기록돼 있다.
실험별 선택 정보와 결과의 의미는 [실험 기록](experiments.md)에서 구분한다.

## 5. 평균 개선을 구간별로 다시 확인하기

| 확인 단위 | 확인하려는 문제 |
|---|---|
| 연도 | 과거 특정 시즌에만 맞는 보정인지 |
| Regular / Futures | 한 경기 유형의 개선이 다른 유형의 악화를 가리는지 |
| 이력 표본 수·신규 선수 | 적은 관측에 과도한 잔차 보정을 하는지 |
| 여러 seed | 특정 초기화에서만 좋아지는지 |
| 투수 단위 bootstrap | 같은 선수의 여러 투구가 있는 구조에서 개선이 안정적인지 |
| ECE 등 확률 보정 지표 | Brier 개선과 확률 보정 변화가 같은 방향인지 |

예를 들어 ENS-032는 전체 평균이 좋아도 신규 투수에서 크게 악화한 혼합을 기각했고,
ENS-044는 Brier가 개선됐지만 ECE는 악화했다. 지표 하나의 개선을 모든 성질의 개선으로 확장하지 않았다.

## 6. 앙상블과 잔차 보정

연구에서 사용한 방법은 크게 세 가지였다.

- **고정 혼합:** 서로 다른 모델의 확률을 일정 비율로 결합한다.
- **조건부 혼합:** 현재 행의 경기 유형·과거 표본 수 등으로 모델 반영량을 정한다.
- **잔차 보정:** 학습·검증 과정에서 남은 오차를 상황·상대 조합별로 설명하고 작은 보정값을 더한다.

보정의 크기, 표본 부족 시 기본값, 확률 범위를 명시했다.
달력 구간, 좌우타 상대 효과, 장단기 상태, 카운트·그래프 정보가 실제로 추가 효과를 내는지
각각의 기준 모델과 비교했다. 후반 실험에서는 기존 보정과 겹치는 효과를 다시 더하지 않는지도 검토했다.

## 7. 같은 행은 같은 입력으로 예측하기

공통 [pipeline](../Preprocess/common/pipeline.py)은 `fit`에서 상태를 고정하고 `transform`에서 현재 행을 변환한다.
평가 배치 내부에서 새 빈도·평균·누적값을 학습하지 않는다.

제출 후보는 단일 행, 순서를 바꾼 입력, 여러 배치 분할에서도 계산이 일치하는지 확인했다.
제출 패키지에 들어가는 계산 경로가 원래 실험과 같은지도 별도로 검사했다.
이 단계는 성능 향상 실험을 대체하지 않으며, 선택한 계산을 제대로 전달하는지 확인하는 단계다.

구현 파일과 테스트별 범위는 [전처리 문서](../Preprocess/README.md), 연구의 결정 과정은
[모델링 기록](modeling.md)과 [앙상블 기록](experiments.md)에 정리했다.
