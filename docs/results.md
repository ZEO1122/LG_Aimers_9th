현재 표는 캡처 기준 결과다. 코드 검증 후 최종 순위, 전체 참가 팀 대비 비율, 특정 최종 제출 ZIP과의 연결은 확정하지 않았다.

종료 시점의 Public 점수를 Private 점수로 사용한다. [규칙](https://dacon.io/competitions/official/236743/overview/rules)은 코드 검증 후 확정 절차를 구분한다.

## 점수만 보면 놓치는 내용

**실행 방식이 달라지면 같은 계열도 결과가 달랐다.** No1-002를 새 최고점으로 연결하지 않은 이유는
ENS-003 재학습 계열의 결과가 이전 제출과 일치하지 않았기 때문이다. 환경과 고정 설정뿐 아니라 실제로 전달된 계산 경로를 확인해야 했다.

**내부 개선이 그대로 리더보드 개선은 아니었다.** ENS-002는 2024 내부 점수가 약 2.57점 올랐지만 실제 제출에서 하락했다.
월을 시즌 상태의 대리변수로 쓰는 선택이 미래 시즌에서도 유지되는지 충분히 확인하기 어려웠다.

**더 낮은 단일 점수의 모델도 쓸모가 있었다.** ENS-032의 XGBoost는 2024 단독 성능이 LightGBM보다 낮았지만,
오차가 다른 구간에서 제한적으로 섞었을 때 개선했다. 반대로 근거가 약한 신규 투수에 비중을 키운 방식은 실패했다.

**나쁜 보정을 빼는 것도 개선이었다.** JJO-003은 모델을 새로 학습하지 않고 State 보정의 일부를 제거했다.
추가 단계가 많을수록 각 단계의 효과와 현재 기준 모델과의 궁합을 다시 확인해야 했다.

## 잘했던 점

- 경기 상황과 이력의 의미를 먼저 정리하고, EDA의 관찰을 구체적인 피처 가설로 연결했다.
- 트리·딥러닝을 병행하면서 단일 성능과 오차의 다양성을 함께 살폈다.
- 연도, F/R, 저표본·신규 선수, seed별 결과를 남겨 평균 개선의 원인을 구분했다.
- 실패한 실험을 기록해 월별 보정, 특정 표현 변경, 과도한 보정 강도를 다시 검토할 수 있었다.
- 제출용 코드에서 원래 계산이 유지되는지 검사하고 성능 채택 여부와 구분했다.

## 아쉬웠던 점

**검증 데이터의 반복 사용.** 2024 결과를 여러 실험에서 확인하면서 새로운 미래 구간에 대한 독립성을 유지하기 어려웠다.
사후 원인 분석의 성과와 새로운 모델을 채택할 근거가 섞이지 않도록 문서에서 구분했지만,
초기에 탐색용·최종 확인용 평가를 더 명확히 분리했다면 결론을 해석하기 쉬웠을 것이다.

**개선 폭과 실험 비용의 균형.** JJO-223처럼 평균 gain이 아주 작고 불확실한 후보,
FT-019처럼 별도 전문 모델을 학습했지만 더 나빠진 후보가 있었다.
실험 전에 최소 의미 있는 개선 폭과 계산 자원을 함께 정하면 후반 탐색의 우선순위를 더 잘 잡을 수 있었다.

**제출 근거의 분산.** 각 실험에는 제출·패키지 기록이 남아 있지만 전역 제출표는 충분히 갱신되지 않았다.
그 결과 팀 캡처 점수와 정확한 최종 소스·ZIP의 연결을 바로 설명하기 어려웠다.
앞으로는 제출 ID, 시각, 실험 ID, 커밋, ZIP 해시, 실제 점수, 채택 사유를 한 줄로 연결해 관리할 계획이다.

## 다시 진행한다면

1. 시간축 비교 기준과 후보 선택용 구간을 먼저 고정하고, 최종 확인 데이터에 접근하는 횟수를 제한한다.
2. 실험마다 한 가지 가설과 최소 개선 기준을 명시한다. 큰 구조 변경은 기존 모델과 짝지은 비교를 먼저 수행한다.
3. 새 모델 추가 전에 기존 보정의 제거·축소 실험으로 상호작용과 불안정한 단계를 확인한다.
4. 전체 Brier와 함께 F/R·신규 선수·확률 보정·추론 비용을 같은 결과표에 기록한다.
5. 제출 직후 결과를 전역 제출표와 소스·패키지 해시에 연결한다.
